# Опора на своём сервере в Казахстане

Как это устроено:

```
GitHub (main) ──► GitHub Actions: проверка и сборка образа ──SSH──► сервер hoster.kz
                                                                    ├─ app    — сайт (Next.js)
                                                                    ├─ caddy  — HTTPS, бесплатный SSL Let's Encrypt, сам продлевает
                                                                    ├─ cron   — письма дня и напоминания, 08:00 по Астане
                                                                    └─ db, auth, rest, storage — своя база (открытый Supabase):
                                                                       данные, вход и файлы, наружу не открыты
```

- **CI** (`.github/workflows/ci.yml`): на каждый pull request и в main проверяет линтер, типы и сборку.
- **CD** (`.github/workflows/deploy.yml`): после каждого слияния в main собирает Docker-образ на GitHub, отправляет его на сервер по SSH и перезапускает сайт, потом проверяет, что сайт открывается. Пока в GitHub нет секретов `DEPLOY_SSH_KEY` и `GEMINI_API_KEY`, выкладка пропускается.
- **Server** (`.github/workflows/server.yml`): ручные действия без входа на сервер: `setup` (первая настройка), `status`, `logs`, `restart`.
- SSL: Caddy сам получает сертификат Let's Encrypt для домена и `www`, сам продлевает. Платить и что-то настраивать не нужно.

## 1. Купить сервер и домен (hoster.kz)

1. Зарегистрируйтесь на https://hoster.kz.
2. **Облачный VPS** → тариф **Cloud 2-8-100** (2 ядра, 8 ГБ памяти, 100 ГБ NVMe), система **Ubuntu 24.04**, дата-центр в Казахстане (Алматы или Астана).
   8 ГБ памяти нужно с запасом под базу данных: по закону о персональных данных её нужно перенести в Казахстан, и она встанет на этот же сервер.
3. **Домены** → проверьте и купите `.kz` (например `opora.kz`; если занят, `opora-app.kz`, `myopora.kz`). Для `.kz` нужны данные владельца (ФИО или ИП, адрес) — так требует реестр.
4. В управлении доменом → **DNS** добавьте две записи типа **A** с IP-адресом сервера: имя `@` и имя `www`.

## 2. Ключ для входа на сервер (вместо пароля)

На своём компьютере откройте **PowerShell** (Windows) или **Терминал** (Mac) и выполните:

```
ssh-keygen -t ed25519 -C opora-deploy -f $HOME/.ssh/opora_deploy
```

На вопрос про passphrase дважды нажмите Enter. Появятся два файла:

- `opora_deploy.pub` — **публичный** ключ, его не жалко показывать. Если при заказе сервера можно добавить SSH-ключ, вставьте его туда. Показать: `cat $HOME/.ssh/opora_deploy.pub`
- `opora_deploy` — **секретный** ключ. Никому не отправляйте и не вставляйте в чат. Он нужен только в шаге 3. Показать: `cat $HOME/.ssh/opora_deploy`

## 3. Настройки в GitHub

Откройте репозиторий → **Settings → Secrets and variables → Actions**.

Вкладка **Secrets** → **New repository secret**:

| Имя | Что вставить |
|---|---|
| `DEPLOY_SSH_KEY` | весь текст секретного ключа `opora_deploy`, вместе со строками `-----BEGIN…` и `-----END…` |
| `ROOT_PASSWORD` | пароль root из письма хостинга. Нужен один раз для первой настройки, потом секрет можно удалить |
| `GEMINI_API_KEY` | ключ ИИ (Vercel → Settings → Environment Variables или https://aistudio.google.com/apikey) |
| `RESEND_API_KEY` | ключ Resend для писем входа (подтверждение почты, новый пароль) и писем дня |
| `SUPABASE_DB_URL` | только на время переноса: строка подключения к облачной базе Supabase (Project Settings → Database → Connection string, режим Session). После переноса удалить |
| `PROD_ENV` | необязательно: дополнительные настройки, образец в `deploy/env.example` |

Открытые настройки (IP сервера, адрес сайта, публичный ключ базы) уже записаны в `deploy/site.env`, в GitHub их добавлять не нужно.

## 4. Первая настройка и выкладка

1. **Actions → Server → Run workflow**, действие **setup**. Скрипт `deploy/server-setup.sh` обновит систему, поставит Docker, создаст пользователя `deploy`, выключит вход по паролю и вход root, включит файрвол (открыты только 22, 80, 443), fail2ban и автообновления безопасности, заблокирует пароль root. Запускается один раз: после него вход root закрыт.
2. **Actions → Deploy → Run workflow**. Через 3–5 минут сайт откроется на `https://ваш-домен` с замком SSL.
3. Supabase → **Authentication → URL Configuration**: **Site URL** = `https://ваш-домен`, в **Redirect URLs** добавьте `https://ваш-домен/**`. Иначе ссылки из писем будут вести на старый адрес.
4. Когда новый адрес работает, в Vercel удалите переменную `CRON_SECRET` (или отключите проект), чтобы письма дня не уходили дважды.

Дальше всё само: каждое слияние в main выкладывается на сервер.

## Если что-то пошло не так

- **Actions → Server → status**: что запущено, память, диск, кто выдал SSL и до какого числа.
- **Actions → Server → logs**: последние строки журналов.
- Откатить: **Actions → Deploy**, откройте прошлую удачную выкладку → **Re-run all jobs**.
- Войти руками: `ssh -i $HOME/.ssh/opora_deploy deploy@IP-сервера`, файлы сайта в `/opt/opora`.

## Своя база данных

На сервере работает открытая версия Supabase: PostgreSQL 17 (`db`), вход (`auth`), API данных (`rest`) и файлы (`storage`).
Снаружи доступны только через Caddy по адресам `https://домен/auth/v1`, `/rest/v1`, `/storage/v1`. Порт базы наружу закрыт.
Ключи базы (`SB_*` в `/opt/opora/server.env`) создаются на сервере при первой выкладке и его не покидают.

Перенос из облачного Supabase: **Actions → Server → migrate-db** (нужен секрет `SUPABASE_DB_URL`). Переносятся схема, права и правила
доступа, аккаунты с паролями (людям придётся войти заново), все данные и файлы из открытых корзин. Потом в `deploy/site.env`
`NEXT_PUBLIC_SUPABASE_URL` меняется на адрес сайта, а `NEXT_PUBLIC_SUPABASE_ANON_KEY` — на слово `server`: выкладка сама возьмёт открытый ключ своей базы с сервера (сделано 09.11.2026).

## Резервные копии

Служба `backup` каждую ночь в 02:00 по Астане сохраняет базу (`db_*.dump`, pg_dump) и файлы (`files_*.tar.gz`)
в `/opt/opora/backups` на сервере и хранит их 14 дней. Список последних копий: **Actions → Server → status**.
Копии лежат на том же сервере, поэтому от поломки самого сервера они не спасут: позже стоит добавить копию
во второе хранилище в Казахстане.

Восстановить базу из копии (на сервере, в `/opt/opora`):
`./dc.sh exec -T db pg_restore -U supabase_admin -d postgres --clean --if-exists < backups/db_ДАТА.dump`
