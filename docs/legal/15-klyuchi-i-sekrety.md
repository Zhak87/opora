# 15. Порядок хранения ключей шифрования и секретов

> Внутренний документ. Черновик. Сверено с `deploy/README.md` и `docs/security/chat-encryption.md` на 21.11.2026. Значения ключей в этот документ **не записываются**.

## 1. Где живут секреты

| Секрет | Где хранится | Покидает сервер? | Если потерян | Если утёк |
| --- | --- | --- | --- | --- |
| `CHAT_ENCRYPTION_KEY` | `/opt/opora/server.env`, создаётся при первой выкладке | нет | **все разговоры с ИИ навсегда нечитаемы** | перешифровать все разговоры новым ключом (п. 4) |
| `SB_*` (ключи базы, JWT) | `/opt/opora/server.env` | нет | пересоздать, все выйдут из аккаунтов | пересоздать, все выйдут из аккаунтов |
| `LIVEKIT_API_KEY/SECRET` | `/opt/opora/server.env` | нет | пересоздать при выкладке | пересоздать |
| `GEMINI_API_KEY` | секреты GitHub → `site.env` при выкладке | да, в GitHub | выпустить новый в AI Studio | отозвать в AI Studio, проверить расходы |
| `RESEND_API_KEY` | секреты GitHub | да | новый в Resend | отозвать, проверить отправленные письма |
| `CLOUDFLARE_API_TOKEN` | секрет GitHub `PROD_ENV` или `server.env` **[уточнить]** | да | новый | отозвать |
| `WEB_PUSH_PRIVATE_KEY` | секрет GitHub `PROD_ENV` или `server.env` **[уточнить]** | да | новый — все подписки на push пропадут | новый |
| `EXPO_ACCESS_TOKEN` | секрет GitHub `PROD_ENV` или `server.env` **[уточнить]** | да | новый в Expo | отозвать |
| `EMAIL_SECRET`, `CRON_SECRET` | секрет GitHub `PROD_ENV` или `server.env` **[уточнить]** | да | новый | новый |
| SSH-ключ выкладки `DEPLOY_SSH_KEY` | ноутбук владельца, секрет GitHub | — | доступ через панель hoster.kz | удалить ключ из `authorized_keys`, новый |
| Пароли от hoster.kz, домена, Google, Apple, Expo | менеджер паролей владельца | — | восстановление через почту | сменить, 2FA |

**Сразу удалить, если ещё лежат в GitHub:** `ROOT_PASSWORD` (нужен был один раз для первой настройки) и `SUPABASE_DB_URL` (нужен был только для переноса из облака, 09.11.2026). По `deploy/README.md` оба секрета после использования должны быть удалены.

## 2. Офлайн-копия `CHAT_ENCRYPTION_KEY` (сделать обязательно)

1. Владелец один раз читает ключ на сервере: `grep CHAT_ENCRYPTION_KEY /opt/opora/server.env`.
2. Записывает его в две копии: (а) менеджер паролей, (б) бумага в конверте или зашифрованная флешка в надёжном месте дома/в банковской ячейке.
3. Отмечает в журнале: дата, где лежат копии (без значения).
4. Не отправлять ключ в мессенджеры, почту, чаты с ИИ, скриншоты.

То же — для `server.env` целиком (без него восстановление сервера из резервной копии займёт больше времени).

## 3. Правила

- Секреты не хранятся в коде, `.env` файлы — в `.gitignore`; `deploy/env.example` содержит только имена.
- Секреты не печатаются в журналах; в сообщениях пользователям — никогда (правило проекта).
- Доступ к секретам GitHub и серверу — только владелец и ведущий разработчик (документ 14).
- При уходе человека с доступом — сменить ключи, которые он мог видеть.
- Раз в год — плановая смена ключей поставщиков (Gemini, Resend, Cloudflare, Expo).

## 4. Смена `CHAT_ENCRYPTION_KEY` (если утёк)

Сейчас готового сценария смены нет: `scripts/encrypt-chats.mjs` шифрует открытые строки одним ключом. Нужна доработка: скрипт, который читает разговоры старым ключом и записывает новым, и временная поддержка двух ключей. **[задача разработчику]** До её появления при утечке ключа: закрыть доступ к серверу, оценить, утекла ли и база (без базы ключ бесполезен), действовать по документу 12.

## 5. Восстановление

Проверять раз в квартал: развернуть резервную копию на тестовой машине с ключом из офлайн-копии и убедиться, что разговоры читаются. Запись в журнал.
